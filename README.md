REST API микросервис на Go для сбора, нормализации и сопоставления (дедупликации) контента отелей, получаемого от различных внешних поставщиков (партнерских OTA-систем).

Проект разработан для отработки архитектурных паттернов бэкенда, работы со сложными SQL-индексами, многослойной архитектуры (Clean Architecture) и интеграционного тестирования.

---

## 🎯 Проблема и решаемая задача

В сервисах путешествий (например, Туту Отели, Ostrovok) одни и те же гостиницы поступают от десятков разных поставщиков (Островок, Броневик, прямые контракты). При этом:
* Названия различаются регистром, кавычками и опечатками (*«Отель Космос»* vs *«космос отель»*).
* У одного поставщика есть качественные фотографии, но бедное описание, а у другого — высокий рейтинг и подробный список удобств.
* Координаты могут иметь небольшие расхождения (в пределах 50–150 метров).

**Сервис решает:**
1. Потоковый приём и валидацию данных через REST API.
2. Автоматическое сопоставление дубликатов по нормализованному имени, городу и гео-координатам (расстояние по формуле Haversine $\le 200$ м).
3. Обогащение (Enrichment) единой карточки отеля лучшими атрибутами (объединение фотографий, удобств, выбор максимального рейтинга).
4. Быстрый поиск отелей по фильтрам (город, минимальный рейтинг, звездность) с пагинацией.

## 🏗 Архитектура приложения

Проект построен по принципам чистой слоистой архитектуры (Clean Architecture):

```
├── cmd/
│   └── server/          # Точка входа: инициализация DI, Graceful Shutdown, HTTP сервер
├── internal/
│   ├── model/           # Доменные структуры: Hotel, IngestPayload, SearchFilter, ошибки
│   ├── repository/      # Слой работы с данными (Memory & PostgreSQL интерфейс)
│   ├── service/         # Бизнес-логика: нормализация, поиск дубликатов, слияние контента
│   └── handler/         # HTTP-роутер, REST-хэндлеры, Middlewares (логирование, recovery)
├── migrations/          # SQL DDL миграции для PostgreSQL
├── docker-compose.yml   # Запуск окружения (API + PostgreSQL 16)
└── Dockerfile           # Двухэтапная сборка минимального production-образа
```

## 🚀 Быстрый запуск

### 1. Локальный запуск (In-Memory режим со стартовыми данными)
```bash
go run ./cmd/server/main.go
```
*Сервер запустится на `http://localhost:8080` и автоматически загрузит 2 тестовых отеля.*

### 2. Запуск в Docker с базой данных PostgreSQL
```bash
docker compose up --build
```

### 3. Запуск тестов (с детектором гонок)
```bash
go test -v -race ./...
```

## 📡 Примеры работы с API

### Проверка работоспособности (Healthcheck)
```bash
curl -X GET http://localhost:8080/health
```

### 1. Добавление отеля от Поставщика А (Ostrovok)
```bash
curl -X POST http://localhost:8080/api/v1/hotels/ingest \
  -H "Content-Type: application/json" \
  -d '{
    "supplier_id": "ostrovok",
    "external_id": "ost-777",
    "name": "«Космос» Отель",
    "city": "Москва",
    "address": "Проспект Мира, 150",
    "latitude": 55.8225,
    "longitude": 37.6472,
    "stars": 4,
    "rating": 8.1,
    "description": "Легендарная гостиница у ВДНХ",
    "amenities": ["WiFi", "Парковка"],
    "photos": ["https://img.example/cosmos1.jpg"]
  }'
```
*Ответ: `201 Created` — отель сохранен с новым внутренним ID.*

### 2. Приём того же отеля от Поставщика Б (Bronevik) — Проверка дедупликации!
```bash
curl -X POST http://localhost:8080/api/v1/hotels/ingest \
  -H "Content-Type: application/json" \
  -d '{
    "supplier_id": "bronevik",
    "external_id": "brn-999",
    "name": "космос отель",
    "city": "Москва",
    "address": "пр-кт Мира, д. 150",
    "latitude": 55.8226,
    "longitude": 37.6473,
    "stars": 4,
    "rating": 8.7,
    "description": "Легендарная гостиница у ВДНХ с панорамным видом на Останкинскую башню",
    "amenities": ["WiFi", "Бассейн", "Завтрак"],
    "photos": ["https://img.example/cosmos2.jpg"]
  }'
```
*Ответ: `200 OK` — система распознала дубликат, объединила удобства, фотографии и обновила рейтинг до 8.7 без создания второй записи!*

### 3. Поиск отелей с фильтрами
```bash
curl -X GET "http://localhost:8080/api/v1/hotels?city=Москва&min_stars=4&min_rating=8.0&limit=10"
```

## ⚠️ Known Issues & Технический долг (Осознанные ограничения)

Проект создавался в качестве учебного прототипа, поэтому содержит несколько архитектурных упрощений:

1. **Упрощенный алгоритм нечеткого поиска (Fuzzy Matching):**
   * *Текущее состояние:* Дедупликатор очищает кавычки, переводит строку в нижний регистр и сравнивает координаты по формуле Haversine ($\le 200$ м). Если один поставщик пришлет *"Marriott Royal Aurora"*, а другой *"Отель Марриотт Ройал Аврора"*, строковый алгоритм их не сопоставит.
   * *План решения:* Подключить триграммный поиск через расширение `pg_trgm` в PostgreSQL или расчет расстояния Левенштейна / Jaro-Winkler для строковых сходств.
2. **Race Condition при параллельном Ingestion (Гонка создания):**
   * *Текущее состояние:* Если два потока одновременно отправят одну и ту же новую гостиницу от двух разных поставщиков, оба потока могут пройти проверку `FindMatch()` до того, как запись закоммитится в базу.
   * *План решения:* Добавить распределенные блокировки (Distributed Lock на Redis) по хэшу `city + normalized_name` или использовать PostgreSQL Advisory Locks.
3. **Пагинация через `OFFSET`:**
   * *Текущее состояние:* Использован классический `LIMIT / OFFSET`. При каталоге в сотни тысяч отелей `OFFSET 50000` заставляет базу читать все предыдущие строки.
   * *План решения:* Перевести на Keyset (Cursor-based) пагинацию по составному ключу `(rating, id)`.
4. **Аутентификация API:**
   * *Текущее состояние:* Эндпоинты открыты без авторизации.
   * *План решения:* Добавить middleware проверки API-ключей для внешних партнеров и JWT-токены с ролевой моделью для операторов.
